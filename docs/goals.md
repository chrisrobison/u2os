# Goals: bounded read-only runs and one-time wakes

Goals sit above runs and actions. An owner can save a draft and explicitly start one bounded, read-only pass, now or at a selected future time. Without a selected wake, `executionEnabled: false` and `nextWakeAt: null` remain truthful. The run's `objectiveStatus` stays `unverified` even if individual read actions succeed. A dedicated one-time timer reuses the existing trigger scheduler; there is no continuous model polling or recurrence.

The native **Goals** view creates and edits drafts, shows real linked runs and resource usage, and offers **Run once (read-only)** while budget remains. Starting the first run makes the goal active and freezes its fields until paused. A stale revision asks the owner to reload instead of overwriting another edit.

**Job research draft** fills only a new unsaved form with bounded evidence/relevance criteria, web-only scope and conservative budgets. Add your own role, location and experience preferences before saving; none are invented. It starts no work or schedule and never modifies another stored goal. Follow the [two-pass owner walkthrough](job-research-walkthrough.md); fixture-tested orchestration is distinct from live-provider/model relevance validation.

The authenticated, CSRF-protected API supports `POST /api/goals`, `GET /api/goals`, `GET /api/goals/:id`, and full-replacement `PUT /api/goals/:id`. A draft contains:

```json
{
  "objective": "Find suitable research roles",
  "completionCriteria": ["Report three relevant open roles with links"],
  "constraints": ["Remote or Bay Area only"],
  "permittedScope": { "domains": ["web"], "consequentialActions": false },
  "budgets": { "maxRuns": 10, "maxModelCalls": 20, "maxTokens": 50000 }
}
```

Use the returned `revision` as `expectedRevision` on `PUT`; a stale edit returns 409 without overwriting the other revision. Inputs are bounded and unknown fields rejected. Only the authenticated owner can retrieve or revise a draft or call `POST /api/goals/:id/runs`. A run requires at least one selected domain; each call creates one linked run using the existing bounded agent path. Only registered tools with category `read` and a domain in `permittedScope.domains` can execute. The `consequentialActions` flag records future intent only; it does **not** permit a send, edit, application, or outreach in a goal run. The policy gate and account binding still apply, and the queue rechecks goal scope before execution.

Only one unfinished run is allowed per goal; a new pass waits until that run is resolved. Run count and model-call budgets are enforced before work starts; provider-reported tokens are accumulated and checked before accepting a model plan or beginning another step. Token spending is only as complete as provider usage reporting; unknown usage is not invented. Cost remains unavailable. Runs, usage, and failures persist across restart. The additive `agent_runs.goal_id` migration leaves unrelated runs and existing data intact. No run is automatically retried just because an HTTP response was lost: inspect the goal's linked runs before invoking another pass.

The owner can inspect a linked run in the Goals view after reload. `GET /api/goals/:id/runs/:runId` checks both goal ownership and the exact run link, then returns current run/step statuses, action IDs, the stored run response, and bounded previews of **executed** read results, with `Cache-Control: no-store`. It omits action arguments and account bindings. Credential-like result fields are redacted; large previews are marked truncated. Pending, blocked, failed, and uncertain steps have no completed-result preview. The UI renders provider/model text as text, not markup. Results are evidence to review, not proof that the completion criteria were met.

**Pause goal**, **Resume goal**, and **Cancel goal** persist across restart. `POST /api/goals/:id/control` takes `{ operation: "pause" | "resume" | "cancel", expectedRevision }`. A changed-state request with a stale revision returns 409; same-state retries are harmless. Pause/cancel blocks new runs immediately and requests safe cancellation of unfinished linked runs. Each run is bound to its original goal revision; a lifecycle revision invalidates old planning, steps, and queued work even after resume. The additive snapshot migration binds older runs once because their active goal scope was immutable before these controls shipped. A provider call already in flight retains its real outcome. Resume permits a new bounded pass only after unfinished work is resolved; it does not replay the old run or automatically start work. Goal cancellation is terminal. Spending and evidence are never reset or deleted by these controls.

To change a started goal, pause it, edit its objective, criteria, constraints, domains, or budgets, then **Save revised goal**. The existing full-replacement `PUT` accepts draft or paused goals only. Saving increments the revision but leaves the goal paused, preserves all linked runs and cumulative usage, and never starts work. Lowering a budget below already-spent resources prevents another pass; raising it explicitly permits more work without resetting the ledger. Resume is a separate owner action. Old runs cannot use the revised scope or regain validity. Run evidence labels the original goal revision and a bounded preview of the original run objective (including its saved criteria/constraints), not the current goal text. Historical observations remain evidence from their original scope, not proof of progress against changed criteria.

**Schedule one read-only pass** takes a local date/time in the native view. `POST /api/goals/:id/wake` takes `{ fireAt: <ISO timestamp>, expectedRevision }`, requires a runnable owner goal, and accepts a future time within 30 days. Only one pending wake exists per goal. The view shows its persisted next wake, original revision, consumed run link, or actionable blocker. Reload to refresh background progress; no completion is implied by consuming a wake. The server must be running for the scheduler to work; a still-pending overdue wake is picked up on a later scheduler tick after restart.

The additive `goal_wakes` table links a wake to its exact goal revision and scheduler timer. Run creation atomically marks the wake started and stores its run ID before model/provider calls. Competing ticks or a restart after that transaction cannot create another run for the same wake, even if the timer completion was interrupted. Inspect an interrupted linked run rather than rescheduling blindly. Pause/cancel and any scope edit invalidate pending wakes in the same transaction; resume never rearms them. Managed timers cannot be edited/deleted through generic trigger routes. Existing queue, account, privacy, and policy gates still enforce every action.

Budgets, stopped goals, or unfinished runs block a due wake without starting a run. Model failure retains the failed run; provider failures retain the actual failed/pending/uncertain step states. The wake is not automatically retried. Review goal state, spending, and linked evidence; resolve unfinished work, then explicitly schedule a new wake if appropriate. Persisted wake blockers are fixed codes, not raw provider error text. Missing token/cost reporting remains labeled unavailable.

The **Search findings** panel retains distinct links from persisted, successful `web.search` actions. Refreshing locally indexes at most 20 previously unindexed actions and 30 results per action, without calling any provider or model. This derived SQLite projection can recover older successful results after upgrade/restart; storage failures roll back the projection so retries do not double-count. Failed, pending, or uncertain actions and model-invented response links are excluded. Source links retain the original run, action, goal revision, observed time, and sanitized account identity; unknown identity is labeled unavailable, and mock sources are labeled **Demo result**.

`GET /api/goals/:id/findings?limit=20&offset=0` is owner-scoped and `no-store`, returns at most 50 findings and the five most recent sources per finding, and reports pending indexing, limited/omitted actions, total findings, and page coverage. The native view pages through results and offers **Refresh findings**. Results over 100,000 characters are omitted; title/snippet previews are limited to 300/2,000 characters. Only HTTP(S) URLs without embedded credentials or credential-like query/fragment parameters are retained. Common tracking parameters (`utm_*`, `gclid`, `fbclid`) are removed for goal-scoped deduplication; meaningful paths, IDs, and fragments are preserved. Each distinct action counts once per URL. First-seen title/snippet evidence is retained; later matches update last-seen time and source count, not the owner's review.

Owners may explicitly mark a finding relevant, dismissed, or unreviewed via the native view or `PUT /api/goals/:id/findings/:findingId` with `{ reviewStatus, expectedRevision, expectedGoalRevision }`. Stale finding or goal revisions return 409; cross-owner or wrong-goal references return 404. Review status persists across searches/restart and records the goal revision under which the choice was made. Scope changes do not silently reclassify old evidence or transfer old relevance judgments to new criteria. Provider text is rendered as text; external links use `noopener noreferrer`. A search snippet, a repeated sighting, or an owner's relevance mark does not verify role availability, objective completion, or an established personal fact. The complete derived finding ledger is not dumped into model prompts.

The selected run evidence view includes a deterministic **Research update**, also returned as `researchUpdate` by `GET /api/goals/:id/runs/:runId`. Distinct links first observed in that run's indexed evidence are listed (at most 20); links first seen in an earlier run are counted separately, not repeatedly listed as new. Multiple searches in the same run do not duplicate update links. First observation is ordered by persisted observation time and action ID; refresh/restart does not recount sources or reset review marks. Only successful `web.search` actions contribute. Updates retain the original run's goal revision and the finding's review revision; old evidence remains historical after scope changes.

"New" is relative to **indexed evidence**, not a claim about a newly posted or available job. Updates report current-run successful/indexed/pending/limited searches and goal-wide pending/limited indexing. The existing 20-action refresh/30-links-per-search limits apply; partial history can change the new/repeat classification as indexing catches up. The owner can refresh findings and reopen the run to advance indexing without provider/model calls. If the derived projection is unavailable, the API/view still exposes authoritative run evidence and a sanitized retry notice. No automatic notification, relevance judgment, or goal-completion claim is generated by these counts.

New goal runs retrieve at most four prior successful read actions from the **same goal and owner**, in currently permitted domains. Current-run actions, unrelated conversations/goals, oversized/malformed results, non-read actions, and failed/pending/uncertain actions are excluded. Reads retain original goal revision and account provenance; old observations are historical evidence, not new instructions or confirmation of changed criteria. Retrieval uses only persisted SQLite evidence, never a provider call. Each raw result is capped at 50,000 characters before parsing, then the existing prior-artifact/observation filter applies tighter item/string/depth/total limits and removes credential-shaped fields.

An already-started run may continue after delayed queue delivery without the browser. The existing queue tick reconciles bounded waiting state, resumes only confirmed prerequisites/checkpoints, and reapplies scope, cancellation, policy, privacy, account and cumulative budgets. Restart/missed events do not replay completed effects; unknown outcomes remain blocked for inspection. This continues the **same run**, not a recurring goal schedule. Reopen its evidence view to see the latest grounded response and statuses; the initial conversation turn is not rewritten into a completion claim. Paused/revised goals cannot revive old queued work after resume.

All historical reads—including public search results—have a private classification floor. Destination policy is reapplied for every planner call, continuation, and fallback. Nested classification labels can only tighten the whole result; a wrapped `sensitive` entry remains sensitive, and an over-budget classification scan fails closed. Omission audits contain source IDs/rules, not result text. Registered prior-item references use only exact items that the chosen destination actually saw, preserving the original account binding outside the prompt. Goal runs require validated references for ID-based reads such as `email.read`: discover the object first or use a visible prior item, never substitute a literal guessed ID when history is unavailable. Normal runtime validation, read-only goal scope, policy, account, and budget checks still apply; historical text cannot authorize a send or expand permissions.

Goal search artifacts can carry separate, server-derived `ownerReviewContext`: at most 12 reviewed finding references for that exact successful action, and at most 4,000 additional serialized review characters across the bounded context. A review URL must match a URL in the actual filtered/bounded source result; oversized/omitted source items cannot leak via metadata. Each review records its goal revision and `appliesToCurrentRevision`; stale reviews remain historical, not silently applied to changed criteria. Review metadata stays separate from provider-supplied lookalikes inside untrusted result data and never changes permissions or establishes personal facts.

Every indexed finding source now retains a conservative historical classification. A review inherits the strictest source classification across that finding—not merely its latest/public source—and is filtered again for each exact model destination, continuation and fallback. The additive migration preserves findings, reviews and raw evidence; existing source rows with unknown classification default sensitive rather than becoming permissive. Such historical reviews can remain available to an allowed local model while withheld from a remote one. Review truncation/restriction audits contain IDs/rules only. Classification controls and broader review retrieval remain separate work.

The job-research starter and two-pass fixtures exercise grounded explanations, deduplication and retained reviews, not real-model quality or verified open roles. Recurring research and owner-driven validation remain before goals can claim to handle ongoing responsibilities. Applications and outreach remain separate consequential actions requiring explicit authorization.
